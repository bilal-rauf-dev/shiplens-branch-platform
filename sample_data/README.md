# Authored fictional sample data

No official sample data was published; this fictional dataset was authored for the ShipLens 1.0 submission. All names, emails and phone numbers are fictional.

These files implement [planning/09](../docs/planning/09-dashboard-and-seed-data.md) §§3.1–3.7 and its historical timeline (§3.9). They contain no passwords or database primary keys. The eight user addresses use the reserved `.test` domain; other email addresses use `example.org`. Phone numbers are fictional `+923000000xxx` values. The bilingual public content is authored in content.csv.

All files are UTF-8 CSV with one header row. Dates use `YYYY-MM-DD`; timestamps include the `+05:00` Pakistan offset; monetary values use two decimal places with a dot and no thousands separator. Empty cells mean no optional value. Semicolon-separated cells contain lists. File row order does not control execution: `events.csv` is sorted by timestamp, preserving file order for ties.

## Files and columns

- **cities.csv (5 rows):** `code` is the natural key; `name_en`, `name_ur` are bilingual city names. Existing migration-seeded cities are reused.
- **branches.csv (5):** `branch_code` is the expected service-generated natural key; `city_code` references a city; `name_en`, `name_ur`, `address_en`, `address_ur`, `phone`, `email` supply the branch profile; `target_status` documents its final state. Creation always starts at Forming; timeline transitions produce the final status.
- **users.csv (8):** `email` is the natural key; `full_name` and `role` define the identity. The first five rows are the published role logins. There is deliberately no password column.
- **assignments.csv (7):** `user_email`, `branch_code` link Branch Leads and HR Leads to their scopes. Quetta's assignment is historical; its branch later closes.
- **teams.csv (3):** the pair `branch_code`, `name` identifies each branch team. Volunteer roles use the existing migration-seeded codes `VOLUNTEER`, `TEAM_LEAD`, and `COORDINATOR`.
- **members.csv (9):** `member_order` is the expected yearly counter order, not a database ID; `full_name`, `email`, `phone` are fictional profiles; `branch_code`, optional `team_name`, and `role_code` reference natural keys; `joined_on` dates the spreadsheet import; `target_status` and optional `left_on` document the final result of later status events. Every imported member starts Active. Members 10–12 are created by accepting applications, not by this file.
- **applications.csv (8):** `application_order` is the expected reference-counter order; `full_name`, `email`, `phone`, `date_of_birth` are fictional adult profiles (18–35 at submission); `branch_code` is the preferred branch; `interests`, `availability` contain semicolon-separated form choice codes; `motivation`, `preferred_language` supply form data. `received_on`, `target_status`, `decided_on`, `decision_note`, optional `team_name`, and `role_code` describe the timeline and HR decision. Privacy consent is granted at the submission event. Application 8 deliberately reuses member 9's email.
- **collections.csv (15):** `ref` is the short planning label; `branch_code` selects the branch; `collection_date`, `amount`, `method`, `receipt_no` are service inputs; `created_at` dates creation; optional `voided_at`, `void_reason` describe the later void event. Receipt numbers C01–C15 are natural lookup keys; actual collection references are generated by the service.
- **transfers.csv (7):** `ref` is the planning label; `branch_code`, `transfer_date`, `bank_reference` are service inputs; `receipt_numbers` lists the whole collections covered, separated by semicolons. Actual transfer references are generated by the service.
- **reports.csv (10):** `ref` is the planning label; `branch_code`, `week_start` identify the report; `target_status` documents its final state; `activities`, `volunteer_hours`, `issues` supply fictional narrative data. Drafts and revisions are created by the existing report services, which may also produce empty drafts for other weeks.
- **content.csv (12):** five page sections (home hero/impact, about story/donations, privacy), three programs (two published, one draft), and four events. Fields are `type`, `slug`, `status`, `sort_order`, `image`, `event_start`, `event_end`, `location_en`, `location_ur`, `title_en`, `summary_en`, `body_en`, `title_ur`, `summary_ur`, `body_ur`. Bodies are Markdown; images come from the four fixed local illustrations. The Content Editor creates every working copy and publishes through CMS services. Content audit events share the final historical timeline timestamp (2026-10-26 09:00 PKT), preserving chronological audit order. Event dates are fixed: 2026-10-17 (past), 2026-11-07, 2026-11-21 and 2026-12-05. Impact copy is authored content, not live financial data.
- **events.csv (102):** `timestamp` is an aware historical instant; `actor_email` selects a real staff actor or is empty for public/system events; `action` names the service operation; `arguments` is a JSON object containing only natural keys and action parameters. Equal timestamps execute in file order, so bootstrap users precede their actions. The first Super Admin is bootstrapped with an unusable password; subsequent users use the account creation service. The importer uses `clock.frozen_at` for each event and commits the whole history atomically.

Target-status columns document expected outcomes; they never bypass services or bind protected status fields. The importer validates all headers before making changes. Load this directory with `python manage.py import_sample_data sample_data/`; demo password setup is handled separately by `seed_demo`.

## Alternative column names

Use `python manage.py import_sample_data path/to/csvs --mapping path/to/mapping.yaml`
to rename incoming headers before validation. The YAML maps filenames to
`incoming_name: canonical_name` pairs; headers not listed retain their names:

```yaml
users.csv:
  login_email: email
branches.csv:
  branch_name: name_en
```

PyYAML's safe loader reads the mapping; executable YAML tags are not accepted.
Missing and unknown columns are reported together for every file before any write.
The importer expects an empty user table and a first system event bootstrapping the
Super Admin. Import and reset restore the same reference rows as the data migrations.
